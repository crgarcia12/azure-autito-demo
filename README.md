## Presenting the demo

1. Open the application and sign in with the Caldova operator account.
2. The overview shows 40 cars across London, Manchester, Birmingham, Bristol, Leeds, and Edinburgh. Select a city, search a registration, or select a car on the map to inspect its state and recent position history.
3. Open **Fleet intelligence** or **Ask fleet copilot**. Try “How many kilometers did the fleet drive yesterday?”, “Which vehicles need attention?”, or “Compare utilisation across our branches.”
4. In Caldova Microsoft 365 Copilot, choose **Agents > Caldova Fleet IQ**. The native Fabric agent answers live data questions. The separately installed **Caldova Drive** Teams app is used for morning notification cards.
5. Open **Morning briefing**. Generate the previous day's report, or send it to the configured Teams personal chat. A receipt prevents ordinary repeated delivery for the same reporting date.
6. Open **Telemetry studio** to inspect committed events or pause/resume the injector. Pausing preserves existing telemetry; resuming catches up the deterministic vehicle timeline.

The data is generated by the included vehicle simulator and actually ingested into Fabric. The dashboard never substitutes hard-coded fleet results or chatbot answers when a service fails.

## Architecture

```text
Azure Maps road routes
    -> Python vehicle telemetry injector
    -> Fabric Eventhouse / KQL database
       -> live map, vehicle health, position history
       -> Delta tables in the FleetIntelligence Lakehouse
          -> Fabric IQ ontology with entities, relationships and mileage rules
          -> Fabric data agent (MCP)
             -> application chat
             -> Microsoft 365 Agents SDK / Azure Bot Service
                -> Caldova Teams / Microsoft 365 Copilot
```

The ontology contains `Vehicle`, `Branch`, `Rental`, `VehicleState`, `DailyMileage`, `Incident`, and `RepairQuotation` entities with actual Lakehouse bindings. Its definition is generated and deployed through Fabric's supported TMDL item APIs.

The data agent uses the native **LakehouseTables** source with the actual discovered schemas, tables and columns selected. Do not replace this with a file-oriented Lakehouse source or invented element IDs. Direct attachment of a generation-2 ontology as a data-agent source returned a Fabric schema-discovery error in this tenant; the published agent therefore queries the governed Lakehouse tables used by the ontology. No failed ontology attachment is represented as a working connector.

Fabric currently does not support unattended service-principal calls to data agents backed by KQL. The Lakehouse tables are refreshed from Eventhouse approximately every two minutes, so the unattended agent can use a supported data source. The map reads Eventhouse directly.

## Telemetry and accounting

- Routes are fetched from Azure Maps, not straight-line connections between cities.
- Every event records vehicle ID, UTC interval boundaries, position, heading, speed, odometer, distance, energy level, tyre pressure, temperature, rental, branch, status, and alerts.
- The timeline and event IDs are deterministic. Retrying an interval does not double-count it: KQL queries deduplicate by `EventId`.
- `DistanceKm` is distance travelled during `[IntervalStart, Timestamp)`. Daily totals sum distances, never odometer readings.
- Reporting uses **Europe/Madrid calendar days**, as configured for the briefing. UK operating locations use Europe/London. Midnight-crossing samples are apportioned by their overlap; daylight-saving days can have 23 or 25 hours.
- `DailyMileage` has one row per car and reporting date, including stationary cars. `IsComplete` marks closed calendar days.
- The injector starts with seven days of history. Live events use 15-second intervals and catch up after restarts or an overnight Fabric pause.
- Telemetry is retained in Eventhouse for 30 days.

## Morning automation

The Azure application is **Always On**, single-instance, and runs one lease-protected worker. At **06:45 Europe/Madrid** it can resume the specific shared Fabric capacity, allowing telemetry to catch up before the operator's morning presentation; the application's custom Azure role grants only capacity read/resume. It does not change the existing overnight shutdown automation.

At **08:00 Europe/Madrid**, the worker verifies that telemetry covers the complete previous day, refreshes the Lakehouse, asks the actual Fabric agent for a briefing, and sends an Adaptive Card to the operator's Teams personal chat. The card contains the verified total and the agent's branch/vehicle analysis. The legacy notification app's interactive Teams composer had a client restriction; use the native **Caldova Fleet IQ** agent in Microsoft 365 for chat rather than relying on that composer.

Application state is stored in SQLite at `/home/data/caldova/state.sqlite3` on App Service's persistent disk. Checkpoints, leases, conversation references and delivery receipts survive process restarts and deployments. This deployment must remain **one App Service instance**; it is not a multi-instance database design.

As with nontransactional external messaging, a crash after Teams accepts a message but before its receipt is persisted can result in a retry. Normal repeated sends for a date with a persisted receipt return the existing delivery status.

## Local development

Python 3.12+ and Azure CLI are required. Select the correct context before provisioning:

```powershell
az account set --subscription d41fd8d2-efeb-4629-82ea-c8f25cd2cc64
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Provisioning scripts refuse to run if the active subscription or tenant is different. Deployment IDs are generated into the ignored `.local\deployment.json`; credentials are not written there.

```powershell
.\.venv\Scripts\python.exe -m tools.provision foundation
.\.venv\Scripts\python.exe -m tools.fabric_provision
.\.venv\Scripts\python.exe -m fleet.simulator seed
.\.venv\Scripts\python.exe -m tools.intelligence
.\.venv\Scripts\python.exe -m tools.deploy app
```

The scoped Fabric ontology tenant setting must be enabled for the `Caldova Drive - Fabric IQ` security group. If Fabric rejects its administrative API update, apply it in the Caldova Fabric admin portal.

Start a local preview against the same live Fabric data:

```powershell
$env:PORT = '8097'
$env:FLEET_WORKER_ENABLED = 'false'
$env:FLEET_REPAIR_WORKER_ENABLED = 'false'
.\.venv\Scripts\python.exe -m fleet.web
```

Leave the local worker disabled while Azure is injecting telemetry. For a standalone injector with the Azure worker stopped, use `python -m fleet.simulator once` repeatedly or run the local web process with the worker enabled. Local state is stored under `.local`, and the local server binds only to `127.0.0.1`.

## Work IQ content generation

The separate **Caldova IQ Content Studio** Entra app is `86fe1707-6faf-4c15-a0c0-756419c316f7`, in the same Caldova tenant. Its delegated permissions and sign-in assignments are limited to the three approved authors and the operator. It has no app-only impersonation permission and no client secret.

The approved batch consists of eight multi-person conversations (64 messages), five actual Teams calendar meetings, and six Word documents. Authors are Aadi Kapoor, Aisha West and Alan Steiner. The Caldova operator is included in every chat and meeting and receives access to the documents, making the context available for permission-aware Work IQ retrieval.

The scenario covers handover, airport capacity, EV readiness, maintenance, mileage reconciliation, corporate rental service, commercial interpretation and executive decisions. Facts are read from Fabric rather than invented; the content plan records its reporting period and snapshot timestamp.

```powershell
.\.venv\Scripts\python.exe -m tools.content_app
.\.venv\Scripts\python.exe -m content_studio plan
.\.venv\Scripts\python.exe -m content_studio login --user AadiK@caldova08667473.onmicrosoft.com
.\.venv\Scripts\python.exe -m content_studio login --user AishaW@caldova08667473.onmicrosoft.com
.\.venv\Scripts\python.exe -m content_studio login --user Alans@caldova08667473.onmicrosoft.com
.\.venv\Scripts\python.exe -m content_studio status
$plan = Get-Content .local\content-plan.json -Raw | ConvertFrom-Json
.\.venv\Scripts\python.exe -m content_studio publish --approve-run $plan.runId
```

Review `.local\content-plan.json` and the six files in `.local\content-documents` before publishing. Messages are sent as each authenticated author through the standard Graph chat API. User tokens are encrypted with Windows DPAPI, never committed or printed. Publication checks every author's identity before making changes.

Meeting invitations are sent only to the approved participants. Meetings have real Teams join URLs, agendas and links to the shared documents. Calendar creation does **not** manufacture meeting attendance, recordings, or native Teams transcripts.

Delivery receipts are stored locally; retries skip completed operations. An interrupted chat/message POST with an unknown outcome stops for reconciliation instead of blindly creating duplicates. Graph meeting transaction IDs and deterministic document paths provide additional retry protection.

Work IQ indexing is asynchronous. Publishing content does not guarantee it is immediately searchable in Copilot. The shared Word documents provide policy and operational context suitable for a separate Foundry IQ knowledge-source connection; this generator does not itself provision that connection.

Health probe: `/health/live`. Fleet, chat, control, map-token and briefing endpoints require the authorized Caldova account in Azure. Teams activities are independently JWT-validated and restricted to the configured tenant and operator.

## Operations and costs

- The shared F2 capacity, App Service B1 plan, and Azure Maps usage incur Azure charges.
- The existing Apollo workspace is separate and was not modified.
- The subscription's private-only Storage policy is preserved. No private endpoint or VNet was created. The initially provisioned empty Storage account is not used by the running application.
- App Service contains the agent credential, not source code or browser JavaScript. Rotate it before the expiration recorded in `.local\deployment.json`; update both `FLEET_AGENT_SECRET` and `MICROSOFT_PROVIDER_AUTHENTICATION_SECRET`.
- Preserve `/home/data/caldova` when redeploying. The deployment bootstrap inserts missing state only, rather than overwriting newer Azure checkpoints or receipts.
- Stop the application's worker before retiring the demo or suspending the shared capacity for an extended period. Never delete or reconfigure the shared Apollo capacity as fleet-demo cleanup.
